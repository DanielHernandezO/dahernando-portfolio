Payment systems operate under constraints that most software never faces: every transaction must be **exactly right**, latency matters in milliseconds, and the system must never lose data.

## The Challenge

When you're processing payments for merchants across Latin America, you deal with:

- **Multiple payment providers** with different APIs, protocols, and SLAs
- **Strict consistency requirements** — double-charging a customer is unacceptable
- **Regulatory compliance** across different countries
- **Real-time monitoring** to detect anomalies before they become incidents

## Idempotency as a First-Class Citizen

Every payment operation must be idempotent. This means designing your APIs so that retrying a failed request doesn't result in duplicate charges.

```go
func (s *PaymentService) ProcessPayment(ctx context.Context, req *PaymentRequest) (*PaymentResponse, error) {
    // Check for existing transaction with this idempotency key
    existing, err := s.repo.FindByIdempotencyKey(ctx, req.IdempotencyKey)
    if err == nil && existing != nil {
        return existing.ToResponse(), nil
    }

    // Process the new payment
    txn, err := s.orchestrator.Execute(ctx, req)
    if err != nil {
        return nil, fmt.Errorf("payment processing failed: %w", err)
    }

    return txn.ToResponse(), nil
}
```

## Circuit Breakers for Provider Resilience

Payment providers go down. It's not a question of *if* but *when*. Circuit breakers prevent cascading failures:

```go
type CircuitBreaker struct {
    failures    int
    threshold   int
    state       State
    lastFailure time.Time
    timeout     time.Duration
}
```

When a provider's failure rate exceeds the threshold, the circuit opens and requests are automatically routed to backup providers.

## Key Takeaways

1. **Design for failure** — Every external call will eventually fail
2. **Idempotency everywhere** — Make every operation safe to retry
3. **Observe everything** — You can't fix what you can't see
4. **Test with chaos** — Inject failures in staging regularly

Building payment systems has taught me that the most elegant solutions are often the simplest ones — clear abstractions, explicit error handling, and relentless testing.
